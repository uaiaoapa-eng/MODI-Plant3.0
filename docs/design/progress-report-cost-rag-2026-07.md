# edu-agent 비용·정확성·RAG·온톨로지 진행 보고서 및 로드맵

- **작성일**: 2026-07-08
- **범위**: EDU-27(RAG·온톨로지·재사용), EDU-67/68/70(비용·출력 감축), 이슈 #84(3-tier 라우팅)
- **결론 요약**: 절감 인프라(3-tier 재사용 + 직접서브)는 **구축 완료·배포됨**. 절감 실현은 이제 **실트래픽 축적과 커버리지 확대**에 달려 있으며, 델타 없는 반복 요청에 한해 **턴당 생성 LLM 비용 ~100% 절감(직접서브)**이 실측으로 확인됨. 전체 절감률은 직접서브 적중률(hit rate)에 비례하므로, 다음 단계는 적중률을 끌어올리는 작업(코퍼스 축적·사전제작·임계 튜닝)이다.

- Sonnet 전환은 `docs/todo.md`에 대기 항목으로 존재 (API 접근 확보 시).

### 1.2 비용 구조 (실측 기반)
- **출력 토큰이 비용을 지배** — 입력 비캐시 대비 5.6배 (`agent/orchestrator_stream.py:65-66` 주석, Langfuse 실측 근거).
- 따라서 절감의 실질 수단은 상한이 아니라 **"재생성 회피"** → LLM 호출 자체를 없애는 직접서브가 최종 형태.

### 1.3 RAG·온톨로지 파이프라인
```
사용자 요청 → intent 분류 → reuse 게이트(rag-search 프록시)
                                │
   MySQL(원천 knowledge_chunks) + Redis Stack(BGE-m3 1024d HNSW)
   + concept centroid(W_CONCEPT=0.45) + 온톨로지 그래프(선수학습→관련→MODI)
                                │
        ┌── tier 판정 ──────────┴──────────────┐
   direct_serve            near              cold
   (저장물 그대로 반환,   (후보 프라임 +      (신규 생성)
    생성 LLM = 0)          자유 generate)
                                │
   빌드 결과(학습노트·설계·코드·MODI키) → /api/writeback → 검색 인덱스 되먹임 (폐루프)
```
- **정확성 기여**: 온톨로지 프라임(개념→선수학습 경로→MODI 모듈→학습노트 카드)이 생성 컨텍스트를 보강. 검색 품질은 centroid+alias 재랭킹으로 8/8 달성(#38).
- **비용 기여**: 같은 파이프라인이 재사용 게이트로 겸용되어, 유사 요청을 감지해 생성 회피.
- **폐루프**: 매 빌드 결과가 write-back으로 코퍼스에 쌓여 시간이 갈수록 적중률이 올라가는 구조. 기존 세션 165건 백필 완료.

### 1.4 3-tier 재사용 라우팅 (이슈 #84 → PR #85, 배포됨)
| Tier | 조건 | 생성 비용 | 근거 |
|---|---|---|---|
| **direct_serve** | 유사도 ≥ TAU_REUSE(0.62) + Haiku 만족도 검증 score≥90 AND 델타 없음 | **0** (검증 ~1k 입력토큰만) | `agent/direct_serve.py` (기본 ON, 킬스위치 有) |
| **near** | reuse/review 판정이나 직접서브 불가 | 프라임 + 자유 generate (~973 tok, COLD보다 저렴·품질 양호) | `agent/reuse.py` |
| **cold** | 후보 없음 | 신규 generate (~1,199 tok) | — |

- **핵심 실측 (#84, D3 하네스)**: forced-edit(REUSE_SEED_EDIT)는 출력 2,408 tok·84s·빌드 실패로 **3축 모두 최악** → 기본 OFF로 확정. "재사용 절감은 LLM 편집이 아니라 저장물 직접 서브에서 나온다"가 검증된 결론.
- 직접서브 만족도 실측: 델타 없는 요청 95~100점(OK), 색/기능 델타 15~20점(거부), 무관 0점 — 유사도만으로는 델타를 못 가르므로 검증 1회가 필수이며, 검증비(~1k 입력) << 생성비(1.2~2.4k 출력)라 accept 시 순이득.

### 1.5 관측(Langfuse) — 튜닝의 데이터 기반
- 매 코드턴: `reuse_decision`, `reuse_top1`/`reuse_cand_score`(near-miss), `reuse_tier`, `direct_served`/`direct_serve_score`, `ontology_primed`, 출력 구성 분해(`output_generate/edit/prose_tokens`), 잘림 감시, 캐시 read/creation 토큰.
- `/api/simulate` + `scripts/simulate_batch.py`: LLM 비용 0으로 정확성(PASS/FAIL)·지연·reuse 결정 분포·커버리지를 배치 측정.

## 3. 절감 가능성 판단

**가능하다 — 단, 절감률은 "직접서브 적중률"의 함수다.**

- **턴 단위**: 직접서브 hit 시 생성 출력 ~1,200 tok → 0 (검증 ~1k 입력토큰만 소모, Haiku 입력은 출력보다 훨씬 저렴). near hit도 COLD 대비 출력 ~19% 감소(1,199→973) + 품질 양호.
- **전체 절감률 추정식**: `절감률 ≈ hit_direct × ~95% + hit_near × ~19%` (코드턴 생성비 기준). 예: 코드턴의 20%가 직접서브, 30%가 near면 생성비 약 **25%** 절감. 교육 도메인 특성상 표준 커리큘럼 요청(같은 예제 반복)이 많아 직접서브 적중률의 상방이 큼.
- **현재 병목**: 실유저 reuse 트래픽 0건 → 실측 절감%를 아직 계산할 수 없음. 코퍼스가 얇고(백필 165건) TAU가 실분포에 맞게 튜닝되지 않음. near-miss 계측(top1/cand_score)이 이 튜닝의 근거 데이터를 쌓는 중.
- **과금 모델 유의점**: 프로덕션이 CLI 구독 모드라 절감은 당장 "요금 감소"가 아니라 **세션 리밋 헤드룸 확대(이슈 #80의 429 완화)와 응답 속도**로 나타남. API 모드 전환 시에는 직접적인 청구액 절감 + 프롬프트 캐시·출력 상한까지 추가 실효.
