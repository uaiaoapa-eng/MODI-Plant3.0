02 · 목표와 핵심 원칙

관측 ≠ 검색, 저장소를 분리한다

Langfuse는 관측 저장소이지 검색(RAG) 저장소가 아니다. Langfuse는 변경 불가한 이벤트 로그(원천)로 두고, 재사용 지식은 큐레이션된 별도 벡터 코퍼스로 역할을 분리한다. 이 한 가지가 설계 전체의 척추다.

목표 = 같은/유사 요청을 매번 LLM으로 생성하지 않고, 검증된 과거·사전제작 콘텐츠를 검색·변형해 서빙 → 비용↓, 품질↑, 지연↓.

03 · 목표 아키텍처

5계층 — 기존 코드 위에 얹는다

L1은 기존 자산 보강, L2~L5 신규. 저장소(빨강)는 물리적으로 분리.

L1

관측 Langfuse+Sentry · 보강

기존 trace/span/generation + Sentry 에러/성능. G1~G4 메타 보강 + G5 피드백 추가.

L2

분류 Taxonomy · router 재활용

intent × domain(=modi_modules 축) × actor × outcome를 enum으로 강제. router.classify() 재활용.

L3

재사용 단위 Interaction Record · 신규

요청→결과 증류 + 품질 신호 + 임베딩. reusability_score 임계 이상만 다음 계층.

L4

RAG 코퍼스 벡터스토어 · 별도

품질 게이트 통과분만 적재. 관리자 사전제작 콘텐츠도 여기로. Langfuse와 분리.

L5

재사용 결정 Retrieval+Policy · orchestrator

유사도·intent·품질 임계 통과 시 Haiku 어댑트 서빙, 아니면 생성. 재사용율을 Langfuse score로 폐루프 측정.

04 · 데이터 소스 통합

Langfuse + Sentry → 백그라운드 자동 축적

두 관측 소스는 상호 보완적이다. 백그라운드 워커가 주기적으로 수집·정제·적재한다.

Langfuse무엇을·얼마에
  • 요청/응답 트레이스 → 재사용 후보 원천
  • 비용·토큰·지연 → 경제성/포화 모니터링
  • 품질 score(빌드성공·에러율) → 게이트 신호
Sentry무엇이 깨졌나
  • ❌→ 에러/예외 → 해당 답변 코퍼스 제외·감점
  • 성능/지연 스파이크 → 문제 패턴 식별
  • 반복 실패 셀 → 사전 제작 우선순위 입력

→ Langfuse(성공·비용) + Sentry(실패) 결합으로 품질 게이트가 정밀해진다. ETL 워커는 기존 Redis를 큐로 활용해 백그라운드 실행(§5).

05 · RAG 스택 결정

무엇을, 어떤 스택으로

원칙: 이미 깔린 것을 최대한 재활용하고, 신규는 최소화한다. 학생 데이터라 프라이버시상 임베딩은 로컬 우선.

벡터스토어+ 신규
단계적 — 검증은 MySQL(임베딩 JSON)+앱 코사인(신규 인프라 0), 운영은 별도 Redis Stack 인스턴스(RediSearch 벡터+메타 필터, 세션락 Redis와 분리). → MySQL 샵이라 pgvector(=Postgres 신규)는 제외.
임베딩+ 신규
로컬 BGE-m3 / multilingual-e5 (한국어 지원, 호출비 $0, 데이터 사내 유지) 우선. 관리형 대안: voyage-3-lite. → 프라이버시+비용상 로컬.
분류✓ 기존
router.classify() 패턴 매칭 + guardrail category 재활용 → intent 분류 LLM비 0.
ETL 워커✓ Redis
기존 Redis 큐 기반 백그라운드 워커 — Langfuse SDK export + Sentry API 수집 → 정제 → 임베딩 → upsert. 스케줄은 APScheduler 또는 컨테이너 cron.
서빙✓ FastAPI
기존 orchestrator_stream에 retrieval 게이트 삽입 (L5). 검색→hit면 Haiku 어댑트, miss면 기존 생성 경로.
저술 파이프+ 신규
관리자 백그라운드 배치 — Opus 캐논 저술 → Sonnet 변형 → 자동검증 → 사람검수 → 적재 (§7,§8).

→ 신규는 벡터 인덱스(별도 Redis Stack)·로컬 임베딩·저술 배치 3가지뿐. 원천은 기존 MySQL, 나머지는 기존 코드/인프라 재활용.

06 · 데이터 모델 (AS-IS → 저장 스키마)

무엇을 저장하나 — 그리고 그 스키마

벡터스토어 스키마 (MySQL 원천 + Redis Stack 인덱스) — 구체

① 원천(source of truth) = 기존 MySQL. 임베딩은 JSON으로 저장(엔진 추가 없음).

-- 재사용 단위 = interaction_record 1행 (요청+결과+메타+임베딩) CREATE TABLE interaction_record ( id CHAR(36) PRIMARY KEY, -- UUID trace_id VARCHAR(64) NOT NULL, -- Langfuse 연결 session_id VARCHAR(64), user_id VARCHAR(64), schema_version TINYINT DEFAULT 1, -- ★ 분류(통제 어휘) — 카테고리 필터 intent VARCHAR(24) NOT NULL, -- create|fix|explain|refactor|extend domain VARCHAR(48) NOT NULL, -- hw:motor+button…(modi_modules 정렬) actor_role VARCHAR(16) DEFAULT 'student', outcome VARCHAR(16), -- success|partial|failed|blocked difficulty VARCHAR(8), coding_type VARCHAR(16), mode VARCHAR(16), phase VARCHAR(16), -- 콘텐츠 request_text TEXT NOT NULL, request_norm TEXT, -- request_norm = 임베딩 대상 response_summary TEXT, artifacts JSON, source VARCHAR(16) NOT NULL, -- ★ 품질 게이트 build_success TINYINT(1), tool_error_rate FLOAT, human_feedback TINYINT, reusability_score FLOAT, -- 운영 model VARCHAR(48), cost_usd FLOAT, tokens_in INT, tokens_out INT, -- ★ 검색 (임베딩은 JSON 배열로 보관) embedding JSON, -- BGE-m3 1024차원 created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP, INDEX idx_cat (intent, domain), -- 카테고리 필터 INDEX idx_gate (outcome, reusability_score) -- 품질 게이트 );

② 운영 검색 인덱스 = 별도 Redis Stack 인스턴스 (세션락 Redis와 분리 · 원천이 MySQL이라 언제든 재구성 가능):

# 벡터 인덱스 정의 (RediSearch) FT.CREATE idx:ir ON HASH PREFIX 1 ir: SCHEMA intent TAG domain TAG outcome TAG # ★ 메타 필터 reusability_score NUMERIC # ★ 품질 게이트 embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 1024 DISTANCE_METRIC COSINE # 품질 게이트 통과분만 upsert HSET ir:<id> intent fix domain "hw:motor+button" outcome success \ reusability_score 0.82 embedding <1024 floats> response_summary "..."

③ 서빙 검색 — 같은 카테고리 + 품질 통과분 안에서 의미가 가장 가까운 top-5 (필터 + KNN 한 쿼리):

FT.SEARCH idx:ir "(@intent:{fix} @domain:{hw\:motor\+button} @outcome:{success} @reusability_score:[0.7 +inf])=>[KNN 5 @embedding $q]" PARAMS 2 q <query_vec> DIALECT 2

검증 단계(P4)엔 Redis도 필요 없음: MySQL WHERE intent=? AND domain=? AND reusability_score>=? 로 후보만 추린 뒤, FastAPI 앱에서 NumPy 코사인 top-k. 신규 인프라 0으로 "재사용했다면?" 측정 가능.

핵심은 이 3가지다 — "재사용해도 되는가"를 결정하는 축. ① embedding(의미가 비슷한가) ② intent × domain(같은 종류·대상인가) ③ 품질 게이트(outcome=success · reusability_score 임계). 나머지 필드는 이 판단을 보조하거나 운영·추적용이다. 저장의 최소 단위는 interaction_record 1행이며, 관리자 사전 제작분도 동일 스키마(source='authored')로 들어간다.

06+ · 구조화 입력 (Structured Intake)

유사 요청을 잡는 진짜 열쇠 — 입력을 구조화한다

RAG 성패의 90%가 여기서 갈린다. 자유 텍스트 유사도만으론 hit이 흔들린다. 매칭 키를 구조화하면 "fuzzy 의미 추측"이 "안정적 조회"로 바뀐다.

자유 텍스트 매칭불안정
  • 같은 의도를 표현이 제각각 ("카운터" / "숫자 올라가게" / "버튼 +1")
  • 학생 개인 코드·모듈이 임베딩을 오염 → 유사도 흐려짐
  • 짧고 모호한 입력("안돼요")은 의미 신호가 거의 없음
  • → hit이 들쭉날쭉, 절감 곡선 과대평가 위험
구조화 매칭안정적
  • 매칭 키 = (intent × domain × 모듈구성) + 정규화 목표
  • 개인 코드 디테일은 매칭에서 제외 → 잡음 제거
  • 하드웨어는 모듈이 유한 → 요청 공간이 열거 가능
  • → fuzzy 추측이 거의 결정론적 조회로

매칭 키는 이렇게 만든다

RAW 채팅 입력"버튼 누르면 모터가 돌게 하고 싶은데 제 코드가 안 돌아가요 ㅠㅠ"
— 구조 추출
+ 정규화 →
intent: fix× domain: hw:motor+button× goal: "버튼→모터 회전"

→ 임베딩은 오염된 원문이 아니라 정규화된 목표 한 줄에 대해, 검색 필터는 intent·domain·모듈에 대해 건다. (§6 스키마의 request_norm · intent · domain 컬럼)

이미 보유
edu-agent는 구조화 신호를 이미 갖고 있다 — modi_modules.py(어떤 물리 모듈), Blockly 블록 상태(어떤 블록), coding_type·phase·mode. 채팅 텍스트보다 훨씬 좋은 매칭 신호가 앱에 이미 흐른다.

입력 환경을 "잘" 만드는 3단계 (UX 균형)

교육이라 무거운 폼은 금물. 구조는 에디터에서 자동으로 뽑고, 질문은 최소로.

수동 수집 (공짜)

에디터 상태(모듈·블록·phase)를 자동으로 구조 신호로 사용. 학생은 아무것도 더 안 함.

경량 유도

의도가 애매할 때만 칩/버튼으로 살짝 — "만들기 / 고치기 / 설명" · 대상 선택. router.classify 재활용.

정규화

자유 텍스트는 짧은 "목표 한 줄"로 요약해 임베딩. 개인 코드 디테일은 매칭에서 제외.

검증에 미치는 영향: Phase 0의 요청 군집도는 raw 텍스트가 아니라 이 구조화 표현으로 측정해야 진짜 hit 잠재력이 보인다. 이렇게 재면 free-text보다 군집도가 크게 올라갈 가능성이 높고, 그때 비로소 §9의 경제성이 현실이 된다.

11 · 실행 로드맵 & 정지점 권고

어디까지 가는 게 좋은가

7단계를 다 갈 필요는 없다. 가치는 앞단(관측·품질)에서 일찍 쌓이고, 실제 $ 절감은 P6에서 실현된다. 규모·실측 결과에 따라 3개의 합리적 정지점이 있다.

누적 전략 가치(관측+데이터+검증+절감) 단계별 노력

→ P4까지 오면 전체 가치의 ~65%를 노력 ~55%로 확보하고, shadow 측정으로 실제 절감폭을 위험 없이 확인한다. 이 지점이 P5~P6 진행을 판단하는 게이트다.

정지점 A · 최소P0–P2
  • 조건 소규모(<1,000명) or RAG 불확실
  • 얻는 것 관측 GAP 해소·품질/피드백 신호·운영 통찰
  • $ 절감 0 (관측 가치로 정당화)
  • 노력 ~3주 · 저위험
정지점 B · 권장P0–P4
  • 조건 대부분의 경우 — 기본 목표
  • 얻는 것 shadow 모드로 실제 절감폭 측정·무위험 go/no-go 데이터
  • $ 절감 아직 미실현이나 확신 확보
  • 노력 ~7주 · 저위험
정지점 C · 완전P0–P6
  • 조건 학생 2,000명+ & P4 측정 양호
  • 얻는 것 실제 절감 실현 + 콘텐츠 팩토리
  • $ 절감 연 $15k+ (2,000명 기준)
  • 노력 ~13주 + 교육팀 검수

P4

벡터 인덱스 + 로컬 임베딩 + shadow

검증은 MySQL+앱 코사인(무인프라), BGE-m3 임베딩, shadow 모드로 "재사용했다면?" 시뮬.~2주 · 무위험 효과 검증 · ◀ 권장 정지점/게이트

P5

콘텐츠 팩토리 (Opus/Sonnet 배치)

기존 콘텐츠 ingest → 빈 셀 Opus 저술 → Sonnet 변형 → 검수 → 적재.~4주 + 검수 · 1일차 커버리지

P6

서빙 게이트 + 폐루프

orchestrator에 retrieval 삽입, Haiku 어댑트, 재사용율 score 측정.~2주 · 절감 실현 · ◀ 완전 정지점

권고: 규모와 무관하게 P0~P2는 즉시(저위험·관측 이득) → P4까지를 기본 목표로 삼아 실제 절감폭을 측정 → 그 데이터와 학생 규모로 P5~P6 진행을 결정. 지금(설계 단계)에서 보면 P4가 "최대한 안전하게 확신을 얻는" 지점이다.

12 · 결론 및 권고

결론

현재 코드는 관측이 성숙해 P1~P2(GAP 보강·피드백)는 즉시·저위험으로 착수 가능하며 RAG와 무관하게 가치가 있다. RAG 본체(P3~P6)는 트래픽 규모에서 정당화되며, 하드웨어의 유한 셀 공간 덕에 사전 제작 + 모델 티어링이 특히 잘 맞는다. 신규 스택은 벡터 인덱스(별도 Redis Stack) · 로컬 임베딩 · 저술 배치 3가지뿐이고, 원천은 기존 MySQL, 나머지는 기존 코드/Redis/Langfuse/Sentry를 재활용한다.

권고 순서: P0(실측) 병행 → P1·P2 즉시 착수 → 규모/실측 결과 보고 P3~P6 진행 판단. 가장 큰 지렛대는 기존 사내 콘텐츠 재활용(저술비 $0) + Haiku 서빙.
