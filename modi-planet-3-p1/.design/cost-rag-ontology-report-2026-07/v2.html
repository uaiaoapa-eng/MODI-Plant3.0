3왜 RAG인가 — LLM만 쓰면 생기는 3가지 문제

문제LLM 단독일 때 벌어지는 일RAG가 해결하는 방식
① 비용 — 같은 것을 매번 다시 만든다 "신호등 만들어줘"가 100번 오면 100번 전부 생성. 실측상 1회 생성 = 출력 ~1,199토큰·~47초이고, 출력 토큰은 비캐시 입력의 5.6배 비용이라 이 낭비가 비용의 본체 한 번 잘 만든 결과를 저장 → 두 번째부터는 검색해서 재사용. 델타 없으면 생성 0회(§7)
② 정확성 — 우리 도메인을 모른다 범용 LLM은 MODI 하드웨어 모듈 스펙, 초등 교육과정, 학생 눈높이 표현을 모름 → 존재하지 않는 API를 지어내거나(환각) 수준에 안 맞는 설명 검증된 사내 자산(학습노트·모듈 스펙·기존 코드)을 검색해 프롬프트에 붙임 → 생성이 사실에 접지됨
③ 휘발 — 산출물이 자산이 안 된다 좋은 결과물도 세션이 끝나면 사라짐. 조직 지식이 쌓이지 않음 write-back 폐루프: 모든 빌드 산출물이 코퍼스에 적재 → 쓸수록 창고가 두꺼워지고 적중률이 올라감
요컨대 RAG는 "검색 기능 추가"가 아니라 비용 구조를 바꾸는 장치다. LLM 단독 비용은 요청 수에 정비례해 늘지만(100요청 = 100생성), RAG+재사용 비용은 새로운 요청에만 비례한다(100요청 중 60이 반복이면 40생성). 교육 도메인은 표준 예제 반복이 많아 이 구조의 이득이 특히 크다.

4왜 온톨로지까지 필요한가 — RAG만으로 안 되는 이유

4.1 유사도 검색의 태생적 한계: "비슷함"은 알지만 "관계"는 모른다

RAG의 검색은 결국 유사도 점수다. 유사도는 다음 질문에 답하지 못한다:

교육 서비스가 답해야 하는 질문유사도(RAG)만으로온톨로지가 있으면
"조건까지 반복"을 배우려면 먼저 뭘 알아야 하나?✕ — 비슷한 문서는 찾아도 학습 순서는 모름○ — while_until → loop, conditional → variable 선수학습 사슬을 그래프로 즉답 (실제 시드 데이터)
이 예제에 어떤 하드웨어(MODI 모듈)가 필요한가?✕ — 본문에 우연히 적혀 있어야만 앎○ — 개념→모듈 uses 관계로 명시적 연결
초등학생이 "마법 상자"라고 말하면?△ — 임베딩이 "변수"와 이어줄 수도, 아닐 수도○ — "변수" 개념의 alias로 등록되어 있어 확정 매칭 (실제 시드: 메모지·마법 상자·비밀 상자…)
이 개념과 함께 배우면 좋은 개념은?✕○ — 실제 세션에서 함께 등장한 개념 쌍(relates_to)이 데이터로 축적됨

즉 RAG는 "무엇이 비슷한가"를, 온톨로지는 "무엇이 무엇과 어떤 관계인가"를 담당한다. 교육 서비스는 정답 코드만이 아니라 학습 경로(먼저 배울 것 → 지금 것 → 다음 것)를 제공해야 하므로 둘 다 필요하다.

4.2 온톨로지에 저장되는 것 — 노드와 관계 5종 (실제 스키마)

온톨로지는 두 테이블이 전부다: 개념 노드(ontology_nodes)와 관계 엣지(ontology_edges). 현재 시드 개념 51개(변수·반복·조건·순차실행·임계값·타이밍·버튼입력·다이얼입력…)가 정의되어 있고, 관계는 다음 5종이다.

4.3 온톨로지가 실제로 개입하는 두 지점

5검색 알고리즘 상세 — 3중 유사도 수식

아래 수식은 전부 실제 구현(scripts/search_lib.py)을 그대로 옮긴 것이다. 각 수식 뒤에 "왜 이렇게 했는가"를 붙였다.

5.1 벡터 유사도 v — "의미가 비슷한가" (가중치 0.40)

질문 q와 청크 c를 각각 BGE-m3 임베딩으로 1,024차원 벡터로 바꾼 뒤, 두 벡터 사이 각도의 코사인을 잰다:

v(q, c) = cos(q, c) = ( q · c ) / ( ‖q‖ ‖c‖ )   ∈ [0, 1]
q·c = 두 벡터의 내적(각 자리 숫자를 곱해 모두 더한 값), ‖·‖ = 벡터 길이. 완전히 같은 의미면 1, 무관하면 0에 가깝다. 같은 방향(의미)인지 보므로 문장 길이에 영향받지 않는다.
  • 왜 코사인인가: "신호등 만들어줘"와 "빨강 초록이 번갈아 켜지게 해줘"는 단어가 하나도 안 겹치지만 의미가 같다 — 단어가 아닌 의미 좌표로 비교해야 잡힌다.
  • 속도: 코퍼스 전수 비교 대신 Redis의 HNSW 색인(가까운 이웃끼리 미리 연결해 둔 다층 그래프)으로 근사 최근접 탐색 — 밀리초 단위. 상위 후보를 넉넉히(top×10, REDIS_FANOUT) 받아 아래 5.4에서 재정렬한다.

5.2 어휘 일치 l — "정확한 단어가 있는가" (가중치 0.15)

질문을 토큰(단어 조각) 집합으로 쪼갠 뒤, 청크(제목+본문)에 그중 몇 개가 나타나는지 비율을 잰다:

l(q, c) = | T(q) ∩ T(c) | / | T(q) |   ∈ [0, 1]
T(x) = x에서 한글·영문·숫자 연속열을 뽑아(정규식 [0-9A-Za-z가-힣]+) 소문자화하고, 불용어("해줘"·"만들"·"그리고" 등)와 1글자 토큰을 제거한 집합. |·| = 집합 크기, ∩ = 공통 원소. search_lib.py:228-241
  • 왜 필요한가: 벡터가 뭉개기 쉬운 고유명사·모듈명("IMU", "ToF", "다이얼")의 정확 일치를 보증하는 안전핀. 반대로 동의어에는 약해서 가중치를 낮게(0.15) 둔다.
  • 예시: 질문 "버튼 누르면 LED 켜줘" → T(q) = {버튼, 누르면, led, 켜줘}. 청크 제목 "버튼으로 LED 제어" → 공통 {버튼, led} → l = 2/4 = 0.50.

5.3 개념 유사도 con — "같은 개념 계열인가" (가중치 0.45, 최대) ★ 온톨로지가 검색에 개입하는 수식

먼저 개념 k마다 대표 좌표(centroid)를 만든다 — 그 개념에 속한 학습노트 청크들의 임베딩 평균:

μk = normalize( (1/nk) Σi∈k ei )
ei = 개념 k에 속한 i번째 학습노트 청크의 임베딩, nk = 그 개수. 학습노트만 쓰는 이유(실전 교훈): 코드·설계 청크를 섞으면 centroid가 파일명·목표 문구 쪽으로 끌려가 개념 매칭이 틀어지는 회귀가 실제로 발생해 수정했다. search_lib.py:109-121 (#3 회귀 수정 주석)

그다음 질문과 centroid의 코사인에, 별칭(alias) 등장 보너스를 더한다:

conk(q) = clip( cos(q̂, μk), 0, 1 ) + Wclex · min(hitsk, 3) / 3
q̂ = 정규화된 질문 벡터 · Wclex = 0.2 · hitsk = 질문 문자열에 개념 k의 alias가 나타난 개수(최대 3개까지 반영). 예: "마법 상자에 숫자 담아줘"에는 변수 개념의 alias "마법 상자"·"숫자를 담"이 나타나 hits=2 → 보너스 0.2×⅔ ≈ 0.133. search_lib.py:103-106, 300-305
  • 왜 개별 문서가 아닌 centroid인가: 개별 청크와의 유사도는 표현 하나에 흔들리지만, 개념 청크들의 평균 좌표는 말바꿈(패러프레이즈)에 강하다. 실측에서 gold 질의 6/8을 centroid가 맞춰 개별 청크 top1보다 우수 → 최대 가중치 0.45의 근거. search_lib.py:33-34 주석
  • 왜 alias 보너스인가: 의미 좌표가 놓치는 판별어("장애물", "깜깜" 같은 도메인 단어와 아이 말투)를 시드 지식으로 보강.

5.4 융합과 판정 — 최종 점수와 3단계 결정

S(q, c) = 0.40·v + 0.15·l + 0.45·conk(c)    →    결정 = reuse (S ≥ 0.62) · review (S ≥ 0.48) · register (그 외)
k(c) = 청크 c의 concept_key. 가중치·임계값은 환경변수로 조정 가능(운영 중 튜닝 대비). 후보는 점수순 정렬 후 중복 제거(같은 노트가 여러 세션에 복제된 경우 최고점 1건만), 사용자 가시성 필터(전역 base 자산은 모두에게, 등록물은 본인 것만) 적용. search_lib.py:249-254, 307-346, 356-361

9데이터 축적 전략 — 얼마나, 누가, 무엇을 저장하나

절감률 = 적중률의 함수이므로(§7), 코퍼스를 어떻게 채우느냐가 곧 절감 전략이다. 세 가지 질문에 답한다.

9.1 얼마나 모아야 하나 — 목표량 산정

1차 목표 자산량 ≈ 개념 수(51) × 개념당 검증 예제 3종 ≈ 150 ~ 200개 검증 자산
"검증 자산" = 빌드 성공 + 만족도 검증 통과가 확인된 code/learning_note 청크. 개념당 3종 = 대표 예제 1 + 주요 변형 2 (예: 신호등 기본 / 버튼으로 시작 / 속도 조절). 현재 백필 165건은 수량으로는 목표 규모지만 품질 미검수 — 검수 승격이 필요한 상태.
  • 진행률 측정 방법 (이미 구축됨): simulate_batch.py가 표준 질의 묶음의 reuse+review 비율(=커버리지)을 LLM 비용 0으로 측정. 목표 단계: 커버리지 30% → 60% → 80%.
  • 어디부터 채울지의 데이터 (이미 쌓이는 중): near-miss 계측(0.48~0.62 구간에서 아깝게 미달한 요청)이 "수요는 있는데 자산이 없는" 지점을 매 턴 기록 — 제작 우선순위가 감이 아닌 로그에서 나온다.

9.2 누가 만드나 — 관리자 사전제작 vs 사용자 축적 (질문에 대한 답)

A. 관리자 사전제작 (curated)B. 사용자 생성 축적 (organic)C. 하이브리드 (권장)
방식관리자 모드에서 표준 커리큘럼 예제를 미리 생성·검수·등록실사용자 요청의 write-back만으로 자연 축적시드는 A로, 롱테일은 B로, near-miss 로그가 A의 제작 큐를 채움
품질통제됨 — 1회 검수로 N회 서브편차 큼 — 미검수 등록물전역 노출은 검수 통과분만 (현 구조 그대로: 등록물은 기본 본인만 노출)
커버리지 속도즉시 (배치로 하루면 51개념 커버 가능)느림 — 콜드스타트 문제즉시 시드 + 지속 성장
실수요 정합어긋날 위험 — 안 쓰는 예제 제작 가능100% 정합 — 실제 요청에서만 나옴near-miss가 실수요를 알려주므로 A의 낭비 제거

판정단독으론 낭비 위험단독으론 너무 느림채택 권장
권장안의 근거 — 질문하신 "관리자가 미리 만들어두면 비용절감이 가능하다"는 직관은 옳다. 사전제작 1건의 생성비는 cold 1회와 같지만 그 자산이 k번 직접서브되면 절감은 k×1,199토큰이므로 k≥1이면 이미 본전이다. 단, 아무거나 미리 만들면 k=0(안 쓰임)이 되므로 ① 교육과정상 반드시 나오는 표준 예제(개념 51 × 3)는 선제작하고, ② 그 외는 near-miss 로그가 "실제로 2번 이상 아깝게 미달한 요청"을 제작 큐에 올리는 방식으로 k가 보장된 것만 만든다. 이것이 §11 로드맵 P2(콘텐츠 팩토리)의 설계다.

9.3 무엇을·어떤 비율로 저장하나 — 카테고리 전략

  • 전량 저장하되, 노출은 게이트: write-back은 모든 빌드 산출물을 저장하지만(비용 0의 부산물), source="registered"로 표시되어 본인에게만 검색 노출된다. 전역(모든 사용자) 노출은 검수 승격분만 — 저장 비율보다 승격 비율이 품질 관리 지점.
  • 카테고리는 이미 자동: 질문하신 "카테고리 기반 자동화"는 이미 구조에 있다 — 모든 청크에 concept_key(51개념) × domain × difficulty × intent가 자동 태깅되므로, 커버리지를 개념×난이도 매트릭스로 보면 빈 칸이 곧 제작 대상이다.
  • 중복은 검색단에서 해소: 같은 개념 자산이 여러 개면 검색이 최고점 1건만 서브(dedup)하므로 저장 중복은 해가 아니나, 승격 검수 시 개념당 대표 1~3건을 지정하는 것이 관리상 깔끔하다.
  • 저장 안 하는 것: 빌드 실패물·가드레일 차단 턴은 등록되지 않음. 향후 만족도 검증 점수를 승격 기준에 재사용 가능(이미 같은 검증기가 있음).

12Summary — 전체 관계도와 핵심 숫자

12.1 다섯 줄 요약

  1. 왜 RAG: LLM 단독은 같은 것을 매번 다시 만들고(비용), 우리 도메인을 모르고(정확성), 산출물이 휘발된다 — RAG는 이 셋을 "저장·검색·재사용"으로 바꾼다.
  2. 왜 온톨로지: 유사도는 "비슷함"만 알고 학습 순서·하드웨어·아이 말투를 모른다 — 51개념×관계 5종의 그래프가 이를 보완하며, 관계 대부분은 자동으로 자란다.
  3. 어떻게 정확하게 찾나: 벡터(의미 0.40) + 어휘(정확 단어 0.15) + 개념 centroid(계열 0.45)의 융합 점수 → 임계 판정 → 만족도(델타) 검증의 이중 안전장치.
  4. 절감은 되나: 된다 — 델타 없는 반복 요청은 생성비 100% 절감이 실측 확인. 전체 절감률은 적중률 함수이며, 편집 강제 같은 우회로는 실측으로 반증하고 폐기했다.
  5. 남은 일: 코퍼스 채우기 — 관리자 선제작(51×3) + 사용자 write-back + near-miss 환류의 하이브리드로 검증 자산 150~200을 모으면 직접서브 30%+가 목표.
